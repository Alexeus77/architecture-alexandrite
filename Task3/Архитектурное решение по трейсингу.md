На текущей архитектурной схеме потери заказа могут происходить как при передаче от фронтенда к бекенду, так и внутри системы бекенда.
Предположим, что передачи от фронтенда к бекенду визуально и опытным путем идентифицируются пользователями системы и основной фокус 
модернизации сместим на внедрение трейсинга в бекенд.

В данные трейсинга включим
- метаданные HTTP запроса (метод, путь, некоторые заголовки, статус-код)
- время и длительность HTTP запроса 
- дескрипторы ошибок
- идентификаторы пользователя и заказа


Мотивация

В данный момент имеем неясное поведение системы, в которой есть потери заказов. Трейсинг и его визуализация позволит оперативно 
наблюдать критические места прохождения сигнала в системе, составить представление о необходимости уделить внимание отдельным узлам,
в том числе системам хранения, подготовит к мотивированной модернизации в части логирования и кеширования.

Предлагаемое решение

Для внедрения трейсинга в текущую систему будем использовать OpenTelemetry Java Agent  для бекенд сервисов Java 
(Shop API, CRM API) и OpenTelemetry .NET SDK. для MES API как middleware.
Для сообщений передаваемых через RabbitMQ необходимо добавить метаданные в формате transparent в заголовке сообщения и пробрасывать их 
во всех бекенд сервисах.
Для сбора телеметрии используем Jaeger all-in-one на начальном этапе. На последующих этапах перейдём на отдельный otel-collector.
[Архитектурная модель контейнеров C4](jewerly_c4_model.drawio.png)

Автоматический мониторинг реализуем через дашборды и алертинг Grafana.

Компромиссы

Как упомянуто выше, на этом этапе не будем внедрять трейсинг в фронтенд части системы для снижения издержек. 
Предположим, что ошибки фронтенда визуализированы, задержки между фронтендом и бекендом минимальны.
Телеметрию для хранилищ и RabbitMQ будем получать из сервисов бекенда.

Аспекты безопасности
Для визуализации трейсинга не будем использовать Jaeger напрямую, используем для этого Grafana, так как этот сервис имеет встроенные 
механизмы авторизации по OAuth и LDAP.
