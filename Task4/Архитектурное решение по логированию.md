На данном этапе ограничимся сбором логов в сервисах бекенда:
    Shop API
INFO
- Создание/отмена/оплата заказа
- Запросы (метод, урл, userid)
- Отправка сообщения в RabbitMQ
ERROR
- Ошибки 500
- Недоступность хранилищ и очереди сообщений

    CRM API 
INFO
- Изменение статуса заказа
- Отправка сообщения в RabbitMQ
ERROR
- Ошибки 500
- Недоступность хранилищ и очереди сообщений

    MES API 
INFO
- Получение задания
- Отправка сообщения в RabbitMQ (переход по всем статусам задания)
ERROR
- Ошибки 500
- Недоступность хранилищ и очереди сообщений

Мотивация
Логирование вкупе с мониторингом повысит наблюдаемость системы, а также поможет в оперативном расследовании инцидентов со снижением издержек и создаст информационную базу для бизнес-аналитики.

Предлагаемое решение
- Для сбора, хранения и анализа логов применим ELK стек
- Конкретный выбор инструмента логирования в бекенд-сервисах оставим на усмотрение разработчиков
- Следует логировать trace_id и span_id везде, где это доступно для связи мониторинга и логирования
- Следует маскировать любую чувствительную информация в логах (user email, логины, пароли)
- Доступ к просмотру логов будет определен для роли разработчика для оперативного расследования инцидентов и для роли аналитика для анализа текущей работы системы
- Индекс сделаем по дате для всех трех бекенд-сервисов вместе с периодичностью неделя (7 дней). Периодичность может быть пересмотрена в зависимости от практики размеров индекса. Максимальный размер определим в 20Gb с rollover политикой.
- Хранение логов определим как бессрочное и сориентируемся в дальнейшем по мере прироста логов к соотношению затрат на хранение
- Для оперативного уведомеления об аномалиях и проблемах используем Kibana Alerting (например, для алерта аномального числа созданных заказов)
