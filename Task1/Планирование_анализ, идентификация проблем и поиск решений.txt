В текущей системе видим три подсистемы:
- подсистему Shop: Internet Shop (front), Shop API (back), Shop Db (database))
- подсистему CRM: CRM (front), CRM API (back)
- подсистему MES: MES (front), MES API (back), MES db (database)

Общими для них являются хранилище файлов для обсчёта S3 и Message Queue на RabbitMq для передачи сообщений между сервисами.

Пользователями являются:
- Внешний пользователь (клиент, физическое лицо) - подсистема Shop
- Seller (продавец, сотрудник компании) - подсистема CRM
- Пользователь API (внешний партнер) - подсистема MES
- Оператор (сотрудник компании, исполнитель заказа) - подсистема MES

Проблемы:
1) Сейчас все сервисы и базы данных системы имеют по одному инстансу, отказ или перегрузка в любой точке может приводить к сбоям и задержкам во всей системе.
2) Внешний API пользователь использует сервис MES API непосредственно, что может привести к сбоям по перегрузке сервиса и потерям заказа.
3) В случае сбоя передачи сообщений через RabbitMq неполученные сообщения уйдут в DLQ. Отсутствие работы с DLQ со стороны сервисов - возможная причина потерь заказов
4) В системе отсутсвует кеширование, что создает неоправданные нагрузки на сервисы и базы данных
5) В системе отсутсвует должный уровень логирования и мониторинга для оперативного обнаружения и анализа проблем

Из перечисленных проблем перечислим инициативы, необходимые для их устранения в порядке приоритетов. 
Приоритеты выбраны качественным анализом по соотношению эффекта и затрат:
1) Анализ настроек RabbitMq: TTL сообщений и размеры очередей, состояние DLQ (уже накопленные сообщения), введение retry-политики и final DLQ
2) Введение мониторинга для RabbitMq, прежде всего по состоянию DLQ
3) Анализ, реализация мониторинга сервисов и баз данных в системе по нагрузке и отказам
4) Анализ сервисов, работающих с RabbitMq на предмет работы с очередями DLQ, реализация retry политики со стороны сервисов
5) Реализация масштабирования для БД Shop Db с read-replica (Shop API пишет в мастер, CRM API читает с реплики)
6) Анализ, реализация масштабирования сервисов и сотальных БД по результатам мониторинга. Прежде всего для MES API
7) Внедрение многоуровнего логирования во все сервисы
8) Добавление кеширования в систему по результатам мониторинга и анализа логов
8) Реализация сервиса бекенда для обслуживания запросов пользователей внешнего API
